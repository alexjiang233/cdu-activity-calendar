# 数据维护操作手册 · v1

面向维护执行者，用户无需逐条人工审核。路径相对于项目根目录，基础维护需要Python 3.10+标准库。旧采集适配器仍依赖完整本地资料与既有工具。

## 检查状态

```sh
python scripts/manage_content.py check
python scripts/manage_content.py history
```

返回当前revision、活动/公告/事实数量，并检查SQLite完整性、外键、结构、隐私和修订哈希。异常时停止，不直接改SQL来绕过检查。

## 首次迁移或恢复公开基线

```sh
python scripts/manage_content.py migrate --release public/index.html --batch-id baseline-唯一批次 --reason "从已验收公开版首次迁移"
```

仅空库可执行。公开仓库网页在根目录时用 `--release index.html`。迁移不重新提取原文，而是无损保留现有字段、来源、年度版本和公开依据。已有库不要再灌网页，以免旧网页覆盖新数据。

## 接入更新

1. 整理代理继续交既有规范包：reviewed.json、source-index.json、正文快照、实际读取的附件、报告和断点，不交任意自创JSON，不直接写SQLite。
2. 在完整维护环境完成原有正文、附件、数字、日期、去重和隐私校验。补全继续使用冻结输入与已确认补丁接口，不覆盖原件。
3. 读取当前revision，按明确基线接入。

```sh
python scripts/manage_content.py sync-legacy --batch-id 唯一批次 --reason "补齐哪些公告的哪些信息" --expected-revision rev-从check取得的值
python scripts/manage_content.py check
```

sync-legacy将旧文件解析与补丁收进适配器，仅在本地完整维护环境可用。公开运行源码不含旧快照和全部采集工具；基础迁移、检查、构建、导出、备份、历史和回退不依赖它们。

有变化时先备份再入库；无变化返回unchanged。批次号不能覆盖历史。基线不符先重新检查，不能强行覆盖。普通更新不得移除历史公告，确有撤回或隐私修复等原因才用 `--allow-removal` 并明确原因；不能为缩短列表删历史。

## 构建与发布

```sh
python scripts/manage_content.py build --output public/index.html
python scripts/manage_content.py export --output work/public-export
```

正常构建只读SQLite，不重跑旧批次。导出catalog.json、batch.json与verification.json，不导出SQL历史、原始快照或私人文件。最终HTML再次执行同一个隐私闸，临时文件成功写完后替换目标，错误不覆盖旧页面。

兼容入口 `python scripts/share_demo.py` 同样从数据库构建网页和离线ZIP；它不再自动接入旧资料。“生成成功”不等于新批次入库。

上传后记录提交号、数据库修订、文件哈希与部署结果，并访问线上页面与冻结快照全文比较，之后才能报告已上线。若迁移后网页全文相同，不必重复上传大HTML；代码可独立提交。

## 查看改动与回退

```sh
python scripts/manage_content.py changes --revision rev-目标更新
python scripts/manage_content.py rollback --target rev-要恢复的版本 --expected-revision rev-当前版本 --batch-id 唯一回退批次 --reason "具体原因"
python scripts/manage_content.py check
python scripts/manage_content.py build --output work/restored/index.html
```

回退恢复资料、词表和公开依据，产生新修订，保留历史。回退不自动覆盖线上网站；验证后再发布。未入正式库的原始资料仍需独立备份。

## 备份和恢复

```sh
python scripts/manage_content.py backup --output data/backups/唯一日期.sqlite3
python scripts/manage_content.py --db data/backups/唯一日期.sqlite3 check
```

备份采用SQLite一致性接口，拒绝覆盖已有目标。库损坏时先保留原库，从备份在独立路径check和build，验证后再切换，不删除原库试运气。

初始库是 `data/campus.sqlite3`，备份是 `data/backups/architecture-baseline.sqlite3`。只剩公开网页也能恢复公开内容，但无法恢复完整修改历史或私人原件。

## 扩展与交接

- 新页面消费catalog投影，不自行读取旧批次。
- 新字段先定义含义、空值、依据、导入与展示位置，写进JSON不代表功能完成。
- 结构变化新增迁移文件并提升user_version，不能修改已执行的001文件冒充迁移。目前仅实现schema 1，未知版本会拒绝打开。
- 本次测试覆盖事务中断、过期基线、重复导入、直接SQL篡改、历史回退、备份读取、隐私、日期和来源重复。
- 3298条队列、OCR与既有暂停约定不因架构改动恢复运行。
